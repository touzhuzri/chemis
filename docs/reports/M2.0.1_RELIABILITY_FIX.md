## 1. 原始缺陷与复现方法

### 缺陷 A：上下文预算裁剪错误

`render_state` 的截断循环只遍历 `decisions / observations /
session_summaries / facts`，`available_tools` 不在其中。44 工具的完整目录
（渲染入状态为 28230 字符；对 `describe()` 输出的测量为 57577 字符，因为
每个 Schema 被序列化两次）单项即超过 24000 总预算，循环只能把 observations
逐条 pop 到空——**模型从未看到任何工具返回的数据**。旧实现还有一个伴生缺陷：
`dict(payload)` 是浅拷贝，`items.pop(0)` 直接改空了状态对象自己的列表。

**复现**（`scripts/m201_budget_before_after.py`，输入全部来自原始验收产物
`data/m2-acceptance-run.json` 的五条真实观察 + `build_live_intelligence_stack()`
的同一 44 工具栈，无任何编造样本）：脚本内嵌修复前算法的逐行副本作为 A 面，
当前实现作为 B 面，两侧各用独立构建的状态（防止 A 面的原地破坏污染 B 面）。

### 缺陷 B：运行轨迹进程内即逝

`_LiveRun` 只存在于启动进程的内存字典。进程退出后 `DecisionRecord`、工具
结果、观察、解读全部不可读；`application.report()` 抛
`SESSION_NOT_FOUND ... in this process`。原验收能被复核，只因运行脚本恰好
在退出前 dump 了 JSON。

## 2. 上下文预算新策略

预算语义明确为**近似字符预算**：`STATE_BUDGET_CHARS = 24000` 不再被当成
token 预算宣传，渲染出的文档内 `context_budget.approximate =
"字符预算，非精确 token 计数"` 如实声明。

`render_state_document`（`agent/intelligence_prompt.py`）的分配规则：

| 优先级 | 部分 | 规则 |
| -- | -- | -- |
| 1 | 研究目标、约束、实体、已持证据 id | 必留；极端超长时截断展示并声明 |
| 2 | **observations（真实工具结果）** | 最新优先，占剩余预算 43%；单条数据可沿 900/450/180 三档预览阶梯收缩，收缩处标记 `data_truncated_for_prompt` 并写入 reasons；最新一条在任何情况下保留（floor 形态） |
| 3 | 工具目录 | 占剩余 33%，四档阶梯：`full`（完整 Schema）→ `focused`（目标最相关的前 K 个带完整 Schema）→ `compact`（名称+用途+参数名/类型+必需事实+审批标记）→ `names`；**任何档位都不丢工具名**，参数缺失由校验器 issues 逐字段回授（分层发现的第二层） |
| 4 | 事实/假设/未决问题/决策摘要/调用签名 | 共占剩余 24%，各段最新优先、逐条计省略数 |
| 5 | `context_budget` 诊断块 | 固定预留 520 字符，永不挤爆它所审计的预算 |

其他不变式：

- **别名永远不进目录**（`_catalog()` 已过滤，测试钉死 36 canonical / 0 alias）。
- **压缩只作用于序列化副本**：`state.observations` 与原始 `Observation`
  对象在渲染前后逐字节相等（有测试）。
- **截断必须自首**：任何省略都写进 `context_budget.omitted` 与
  `truncation_reasons`，并置 `state_truncated`；未截断的状态只带
  `context_budget`、不带 `state_truncated`。
- 每条 `DecisionRecord` 新增 `context_budget` 字段，记录该轮 prompt 的
  逐段占用——审计可以回答「模型当时看见了什么」。
- Prompt 版本随之升为 `m2.0-intelligence-2`；SYSTEM 增加预算规则段与
  「解读必须引用 observations 中真实出现的数据」的硬性要求。

## 4. Observation 保留情况

- 44 工具 + 咖啡因观察：最近观察 100% 保留，分子式/分子量逐字符进入 prompt。
- 44 工具 + 10 篇文献标题的观察：观察保留，标题头部逐字进入 prompt
  （超出 note 阶段 1500 字符预览的部分以 `truncated_preview` 声明，原文在
  运行记录中）。
- 工具数 4 → 12 → 24 → 36 递增时，观察保留数恒 ≥ 1、`C8H10N4O2` 恒在
  prompt——工具越多信息越少的反规模现象被回归测试钉死
  （`tests/ai/test_intelligence_context_budget.py`）。
- 60k 字符的病态观察：保留、收缩到 floor、显式标记，整体预算不破，
  更早的观察不被株连。
- 原始 `Observation.data`（含 60k 原文）在渲染后逐字节不变。

## 5. 持久化模型与数据结构

复用现有 SQLite / KnowledgeBase 加表约定（additive，schema 版本保持 v1，
`initialize()` 在旧库上补齐新表——与 M1.5 study_context 表完全同一机制）：

**`ai_research_turns`**（PK: study_id, session_id, decision_id；append
position 排序；`ON CONFLICT DO UPDATE` 幂等）——每轮一行：
`record_json`（完整 `DecisionRecord`，含校验裁决、token、`decision` 原文）、
`step_json`（`ResearchStep`）、`tool_name / arguments_json`、
`tool_result_json`（原始 `ToolResult`）、`observation_json`（观察序列化，
不含内存 `raw` 句柄）、`interpretation_json`（`ScientificInterpretation`
**独立列**——解读永远不在观察里）。resume 的续段以新 decision_id 追加，
不与前段冲突。

**`ai_research_runs`**（PK: study_id, session_id；upsert）——运行终态摘要：
goal、mode、status/outcome/reason、起止时间、模型 provider/名称（无凭据）、
预算实际消耗、token、证据/假设 id、未决问题、失败、诊断、awaiting/
completion/blocked 载荷、record_count。

新增模型 `core/models/research_trace.py`（`ResearchTurnTrace` /
`ResearchRunTrace`）、服务 `services/research_trace.py`
（`ResearchTraceService`：只读写行，不 import agent/llm/repositories，
无任何执行路径——有架构测试钉死）。写入经 `scrub()`；`scrub` 的凭据词
改为**整段匹配**（`input_tokens` 是计数不是凭据，之前被子串规则误杀成
`"[REDACTED]"` 从而破坏整数回读；`Authorization`/`api_key`/`token` 作为
独立段仍然全部脱敏，有测试）。

写入时机：循环内每轮结束 flush 一次（进程在轮间崩溃时，已完成的轮次都在盘上，
且不存在半截行）；运行装配后写 run 摘要。sink 写失败 = 一条 diagnostic，
研究本身照常完成，**绝不伪装成功**（有测试）。

`DecisionRecord` 与研究上下文、GoldenCase 的隔离均未改变：agent view
在同一数据库上经过一次完整 AI 运行后仍读不出任何隐藏参考材料（有测试）。

## 6. 跨进程读取结果

读取路径：`get / decisions / report / live_result` 先查内存，未命中则
`find_ai_research_run(session_id)` 定位 study，按 position 恢复全部
`DecisionRecord` 顺序，`run_result_from_trace` 重建成
`IntelligenceRunResult`（观察经 `Observation.model_validate` 回读，
解读在自己的字段，completion/blocked/awaiting 按原类型还原）。重建对象
进入只读缓存，**不进入 `_runs`**——`answer / cancel` 仍要求活实例并给出
明确错误：**审计恢复 ≠ 任务恢复**。

演示（真实验收运行的产物库）：

- 同进程新 `ResearchIntelligenceApplication` 实例：6 条决策顺序、工具名、
  校验结果、证据 id、报告正文与原进程一致（逐字段等价测试
  `test_the_rebuilt_result_matches_the_live_one_field_for_field`）。
- **真实子进程**（`sys.executable -c ...`，独立解释器 + 独立数据库连接）：
  读回 6 条决策、正确工具序列、渲染出 `# AI 研究报告`；自动化测试
  `test_a_true_second_process_reads_the_trail_and_renders_the_report`
  每次回归都跑。

## 9. 尚存局限

1. **预算仍是字符近似**，不是 tokenizer 计数；不同 tokenizer 下同一文档
   的实际 token 数会有出入（已在文档与 prompt 内如实标注）。
2. **focused 档的相关性排序是拼写匹配**（目标中的英文/ASCII token 与工具
   名称、描述的包含关系）。纯中文目标下排序退化为稳定的字典序——工具名
   一个也不丢，但「最相关优先」在中文目标上没有信号可用。
3. **目录压缩后，非焦点工具的完整 Schema 需要一次被拒绝的调用才能拿到**
   （校验器 issues 逐字段回授）。这是分层发现的既定代价：多一次模型往返。
4. **审计读取按 session_id 定位**（内容哈希，持有者即有权读）。这不是
   枚举接口，但也意味着它与现有 HTTP 读取路径一样不是身份认证——
   与 M2.0 的既有边界一致。
5. **暂停任务的跨进程恢复仍未实现**（且本任务明确不要求）：`answer` 只能
   由启动进程执行；本修复交付的是审计轨迹的跨进程可读，不是任务续跑。
6. run 摘要按 (study, session) upsert——**同 session 的最新段覆盖摘要**；
   各段的逐轮行都在（按 decision_id 追加），但跨段的历史摘要不单独保留。
7. 真实复验只有一次运行、一个模型（MiMo）；「结果驱动调整」在第 6 轮获得
   了首个可验证实例，但样本量是 1，不能外推为一般能力。
8. 本轮未提交 git（按要求）；`uv.lock` 保持未跟踪、未修改。
