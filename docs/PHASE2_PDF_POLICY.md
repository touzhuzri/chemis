# PDF policy

A PDF is a layout file, not a database. Everything below is a statement about
what this extraction layer does **not** give us, written down so that nobody
later mistakes its output for something it is not.

## 1. The parser

| Property | Value |
|---|---|
| Library | `pypdf` 6.19.0, pinned |
| Licence | **BSD-3-Clause, CONFIRMED** — upstream `py-pdf/pypdf` LICENSE read directly |
| Pure Python | yes, `py3-none-any` wheel |
| Python | `>=3.9`; running on 3.10.11 |
| Runtime deps | `typing_extensions>=4.0` only |
| Where it lives | `sources/pdf.py`, and nowhere else |

PyMuPDF stays **EXCLUDED**: AGPL-3.0 / commercial. It is a better extractor and
that is exactly why it is the wrong dependency for this project.

The version is pinned for the same reason `rdkit` is: the parse layer's output is
part of our evidence provenance, so a silent parser bump is a silent change to
text we have already quoted.

## 2. What this extraction does not guarantee

`extract_text()` gives you the character content of a page in roughly reading
order. It does not give you:

- **two-column reading order** — a two-column page typically comes out
  column-interleaved or column-by-column, and we do not reorder it
- **table structure** — cells are text, not a table
- **chemical structure diagrams** — they are images and yield nothing
- **text inside images** — no OCR, and none is attempted
- **superscripts and subscripts** — `H2SO4`, `Na+` and `SO₄²⁻` are not reliably
  distinguished; a chemical formula may come back with characters in the wrong
  order
- **reaction schemes** — arrows, reagents above and below, conditions
- **ligatures, hyphenation across line breaks, footnote markers**
- **which font weight, size or position a character had** — everything is flat text

The output is therefore **extracted text, not scientifically verified text**, and
`DocumentPage.parser_normalized = True` says so on every page.

## 3. Structure images are not processed

A chemical structure in a PDF is a picture. We do not OCR it, do not run
DECIMER, do not attempt image recognition of any kind.

A future extension would be `PDF → image region → DECIMER`, and the
`image region` step does not exist yet. Pretending a formula was extracted from
a diagram when it was not is the kind of error that survives into a synthesis
plan, so the capability is absent rather than approximate.

## 4. What we will not build here

- a PDF *downloader* — files come from the user's filesystem, always
- a publisher scraper, for any publisher
- any use of Crossref `link[]`, OpenAlex `content_urls`, or an Unpaywall
  `url_for_pdf`
- a browser, a login, a session, a CAPTCHA path, an institutional proxy
- OCR, image models, multimodal anything

`fulltext_url` from a provider is still not a permission. A local file is not a
permission either. It is an input we were handed.

## 5. Quoting rules

`Evidence.raw_quote` is the text the parser produced, unmodified: not
paraphrased, not summarised, not translated, not reflowed by a model. When the
parser normalised whitespace or line breaks, that is recorded on the page and in
the docs, rather than the output being presented as byte-level file text.

## 6. Character ranges

`Locator.char_range` is an offset into the **extracted page text**. It is
recorded whenever we can produce it honestly, which is when the passage came
from `search_document` slicing a page we hold in memory.

It is *not* an offset into the PDF content stream, and it is not invented where
the parser cannot supply one. Page, section and quote are always available as
the coarse coordinates; a fabricated character range would be worse than none.

## 7. Size limit

`DEFAULT_MAX_DOCUMENT_BYTES = 100 MiB`, overridable with
`CREA_MAX_LOCAL_DOCUMENT_BYTES`.

**This is a resource-protection limit, not a PDF limit.** The PDF specification
has no maximum file size. The number exists so that pointing the tool at a
disk image, a video or a directory costs a clear error rather than an afternoon
of memory pressure. It is deliberately generous: far above any single paper,
far below anything that hurts.

## 8. File validation order

```
exists → is a regular file → non-empty → within size limit
       → first bytes are %PDF- → parseable
```

The `.pdf` extension is a claim by whoever named the file and is never trusted
as evidence of anything. A file called `actually-not.pdf` containing a shell
script is rejected with `NOT_A_PDF`, not parsed.

## 9. Test documents

Every PDF in the test suite is generated by `tests/fakes/pdfs.py` — hand-written
PDF bytes, `origin = SYNTHETIC`. No real paper is in this repository, and none is
fetched to make a test pass.

The generated documents are single-font, single-column and plain. They exercise
page numbering, text extraction, heading lines, ragged whitespace, repeated
running headers, and a document with no experimental section. **They deliberately
do not** exercise two-column layout or embedded figures, because generating
those faithfully is a PDF-writing project of its own and a fake version would
test the fake rather than the parser. Those limitations are real and documented
here rather than staged in a fixture.
